# Module hook catalogue

Stage 11 fixes the hooks through which expansion modules change the rules. The types live in `packages/engine/src/core/modules/types.ts` (`Hooks`) and the composition in `core/modules/registry.ts`.

## Ordering and composition

Hooks run in module order: dependency order first, then module id. `createRegistry` computes that order once, so it never depends on the order modules are passed in. There are two kinds of hook:

- **Accumulator hooks** take the value built so far as their last argument and return a new value. The first module receives the caller's starting value. Where base owns the default, base passes its own constant as that starting value, so a hook only needs to express a change. For example, `bankInit` starts from the 19-card base bank, and `five-six` maps each kind to 24.
- **State hooks** take and return the whole `GameState`.

Hooks never mutate their arguments. The kitchen-sink test in `packages/engine/test/kitchen-sink.test.ts` checks that every hook below is called, that a dependency's hook runs before its dependent's, and that registration order has no effect.

## Card kinds and extra dice

The card kinds of a game are the keys of `state.bank`, so `cardKinds` and `bankInit` must agree. Hands, costs, trades, steals and discards are kind-generic; a module's own kinds appear as extra keys of `seat.resources.min/max` and `priv.hand`. A `diceSpec` extra die adds an `extra` list to the dice request and an `extra: { [id]: face }` key to `DICE_RESULT`. Without extra dice neither key exists, so base payloads are unchanged. If a 7's discards end and the `robberLike` hook leaves no legal hex, the robber step is skipped.

## Turn flow

`END_TURN` asks `turnFlow` for frames. With none, the next turn starts at once, as it did before stage 11. Otherwise, base replaces the ending phase with a `turnEnd` marker and pushes the frames so the first one is on top. The owning module leaves its frame with `finishTurnFlowFrame`. When only the marker is left, the next seat's turn begins in the same input. While the marker is on the stack, nobody can win or claim victory: the ending seat's turn is over and the next seat's has not begun. The next seat's public points are checked when its turn begins.

## Decks and draws

`decks` returns every physical deck a game uses, as `Record<deckId, { cards: Record<cardType, count>; reveal: 'private' | 'public' }>`. Base contributes `dev` (private) and the `devDeck` result is folded into it first, so `five-six` still only overrides `devDeck`. A module adds its own entries, for example `fog` (public) for seafaring or `progress-science`, `progress-trade` and `progress-politics` (private) for knights. `decksFor(config)` returns the result with ids in ascending order; the P2P deck ceremony shuffles and locks each deck under that order. A physical card is `${cardType}#${n}`. The `card` fields below are card types, the keys of `cards`. Base `initializeState` gives every declared deck `{ remaining: total, drawn: [] }`; a module's own `initializeState` may replace an entry.

A draw is a `random` pending whose request is `{ type: 'draw', deck, seat, slotId, remaining, ... }`. `remaining` must equal the deck's public `remaining`, and the resolving handler must append `{ slotId, seat }` to `state.decks[deck].drawn` and decrement `remaining`, because the P2P ledger checks both against its position cursor.

- **Private draw** (`reveal: 'private'`): `systemType` is `CARD_DEALT`. Push a base `drawDev` frame with data `{ seat, slotId, deck }` (`deck` defaults to `dev`). The resolving input is `{ kind: 'system', type: 'CARD_DEALT', deck, seat, slotId }`, and only the drawer learns the card, through private input data. A frame above a `turnEnd` marker works: leaving it starts the next turn.
- **Public draw** (`reveal: 'public'`): the request adds `public: true`, and `systemType` is the module's own system input type (never `CARD_DEALT`). The resolving input is `{ kind: 'system', type: <systemType>, deck, card, ...echoed }`, where `echoed` is every other request field except `type` and `public` (so `seat`, `slotId`, `remaining` and any module fields). `publicDrawInput(pending, card)` builds it, and every driver and the P2P ledger use that function. `isPublicDraw(pending)` recognises the request. The module's handler declares the echoed keys in `keys`, validates them against its frame, records the card, and emits `{ type: 'deck-card-shown', seat, deck, slotId, card }` so resource accounting sees the deck advance. It leaves a turn-flow frame with `finishTurnFlowFrame`.
- A request's `public` flag must match the deck's declared `reveal`; the P2P ledger rejects a mismatch.

Seafaring's fog uses two public decks, `fog-terrain` and `fog-token`, with the system input `FOG_REVEALED` and an extra `hex` request field; a land hex draws its terrain and then its token from one `fogReveal` frame (see `docs/rules/seafaring.md`).

A draw frame may sit under a module frame that carries on after the deal (`afterDraw`). Knights pushes one `drawDev` frame per draw above its own `progress` frame, so the drawers are dealt to one at a time, and closes the `progress` frame (victory checks, discards, the held-back roll) from the hook. A card slot may carry a public identity (`known`, a card dealt again from a module's own public queue: effect `card-slot-known`, no deck position) and may change hands (`card-slot-moved`, the Spy). See `docs/rules/knights.md`.

Sources outside the engine resolve draws. In local and simulation play a seeded source pops a hidden stack per deck; the seed is separate from the board seed, so the order is independent of it. Online, no seed decides a public draw: see the 2026-09-28 decision on module decks in `DECISIONS.md`.

## Board fixtures

A fixture is `{ id, module, slot, footprint, orientation, art }` in `board.fixtures`. The field is present only when a module declares a fixture, so boards without fixtures hash exactly as before. Rules never read fixtures. The anchor stays a sea-frame hex for every rule, and robber, harbor and production code only look at land hexes and harbor edges. A board with too few slots fails genesis with `NO_FIXTURE_SLOT`. Slots are assigned after every `buildBoard`, from `boardSpec` asked with the **built** board as `config.board`: a board a module generates at genesis (the Open Sea archipelago) gets its slots from itself, and a fixed or explicit board gets the same slots as before.

The renderer draws no sea tile on a footprint cell and runs the board's wooden frame around the footprint as well as the board, so fixture art sits inside the frame like any tile.

A slot's anchor is a sea-frame hex that touches land and has no harbor. Its outer hex is the next hex straight out from a land hex through the anchor, and lies beyond the frame. `boardShapeProblems` checks every shape. The fixed slots are:

| Shape      | Slot         | Anchor   | Outer    |
| ---------- | ------------ | -------- | -------- |
| `standard` | `north`      | `h:0,-3` | `h:0,-4` |
| `five-six` | `north-west` | `h:1,-4` | `h:1,-5` |

## Route graph

`routeGraph` returns `RouteGraph`: `edges` (`id`, two `vertices` and an optional `kind`), `blocked` vertices and optional `transitions`. `longestTrailLength` finds the longest edge-unique trail. A blocked vertex (an opponent building) can end a trail but is never passed through. Two edges of the same `kind` always join at a shared vertex. Edges of different kinds join only at a vertex listed in `transitions`, so a seafaring module lists the seat's own settlements and cities and a road that meets a ship at an empty vertex does not connect. Base edges have no `kind` and no `transitions`, so every join is allowed and the result is the plain longest road. The algorithm takes a predicate, `TransitionAllowed(vertex, from, to)`, and `kindTransitions(transitions)` builds the kind-based one. A hook that adds `kind` to some edges must give every edge a kind, because an untyped edge and a typed edge count as different kinds. The optional `anchors` list vertices holding the seat's own non-building pieces (knights): seafaring closes a shipping route at them as at a settlement, and a ship never connects through a `blocked` vertex. Longest-route rules never read `anchors`.

## Sea-aware boards

Board hexes may use the terrains `sea`, `gold` and `fog` (`SEAFARING_TERRAINS`). Land is every terrain except `sea` and `fog` (`isLandTerrain`), so a fog hex counts as water until a reveal replaces it. Sea hexes stay in `board.hexes`, so the board graph has vertices and edges around them. Base uses these classifications, which are identical to the old behaviour on a land-only board:

- A settlement needs a vertex that touches at least one land hex (`vertexOnLand`).
- A road needs an edge that is not a sea edge (`edgeKindOf` is `land` or `coastal`). `classifyEdge` gives `land` for land on both sides, `coastal` for land on one side (a land hex on the outer rim counts, with off-board as its other side, as do sea and fog) and `sea` for no land side.
- The robber's legal hexes are land hexes only (`isLandHex`). The base invariants require the robber on a land hex and each harbor on a coastal edge.
- Production and setup resources come from `TERRAIN_RESOURCE`, which has no `gold` entry, so base ignores gold. A module's `production` hook pays it.
- `detectIslands` returns the connected components of land hexes, each named by its least hex id. `boardIslands(state)` caches them per hex list, so a reveal that replaces the hexes recomputes them.

A seafaring shape sets `seafaring: true` in `BoardShapeSpec`. Its `hexes` list every hex including sea, and only fixed boards are accepted (`generateBoard` rejects random layouts). Validation still checks the terrain and token bags, but sea and fog carry no token, gold carries one, the robber may start on any land hex and harbors need only be on coastal edges of the supplied board. Without the flag, `sea`, `gold` and `fog` are rejected. `coastEdgeCycle`, `frameHexes` and `seaSideOfEdge` still take land hexes only. Pass `landHexes(board.hexes)`, and expect `coastEdgeCycle` to throw on a board with several islands. Use `coastalEdges` there.
