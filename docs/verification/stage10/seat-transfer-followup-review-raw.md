## Findings

### Same-device / fresh-device journal promotion

1. **Constructor guard doesn't check safety bytes (design gap, ln 160 vs indexed-db-protocol-journal.ts:94–97).** `journalAbsent` is computed from `genesisBytes`, `consensusBytes`, `entryKeys.length` and cross-checked only against `bindingBytes`. It never inspects safety `bytes`. The design requires "fresh-device import requires genesis, entries, safety and active binding **all** absent; any partial journal ... fails" (ln 160), but the shown constructor path would treat a store with leftover safety bytes and no genesis/binding as `journalAbsent = true` and let it pass. The second guard block (ln 250–255) does check `bytes === undefined`, but that's evidently a different method (read/sign path), not the constructor. If `promoteTransfer`'s "genesis, entries, safety and active binding all absent" precondition (ln 160) isn't re-implemented independently inside that transaction, an orphaned safety record could survive a "fresh" import undetected.

2. **No explicit rule for multi-seat-per-device.** The atomic guard (ln 94–105, 250–255) enforces one binding per journal keyed by `gameId`. Design only enumerates two promotion shapes — fresh-device (all absent) and same-device return/re-key (existing binding matches the retired controller) — and states "any ... unrelated binding fails" (ln 160). A device that legitimately hosted a *different* seat's journal for the same game (e.g., local hot-seat use) has no promotion path at all; it's implicitly excluded rather than explicitly addressed. Confirm this is intentional (one seat per device instance) rather than an oversight.

3. **Source limitation — locking order unverifiable.** Design ln 162 requires "acquire locks in one documented order," a game-wide active-journal lease distinct from the per-authorization staging lock, and CAS at the IndexedDB layer to cover cross-device races. The `game-writer.ts` excerpt (ln 20–36) shows only the `GameWriterLeaseError` class and the start of a release-signal promise — no acquisition order, no CAS, no interaction with staging locks. Cannot confirm the implementation satisfies ln 162 from what's given.

### Certified cancellation / retry

4. **No liveness/timeout criterion for triggering `transfer-cancel` (design gap, ln 113/168).** The design says "a failed destination requires cancel followed by a fresh authorization" and "if it loses staged keys or private material, the old quorum certifies transfer-cancel," but never defines what makes a destination officially "failed" versus merely slow, pre-activation. Post-activation liveness at least gets a rule (ln 170: old key retires regardless, game pauses). Pre-activation, there's no bound — an indefinitely silent destination just leaves the transfer pending forever unless quorum manually judges it dead, with no protocol-level signal for that judgment.

5. **No stated exclusivity between `transfer-cancel` and activation for the same authorization (design gap, ln 113/170).** Mutual exclusion is spelled out for recovery-vs-transfer ("reject recovery-authorize while any transfer is pending," "reject transfer authorization while recovery is pending," ln 113) but not for cancel-vs-activate on the *same* pending transfer. Nothing forbids the old quorum from certifying both a cancellation and an activation for one authorization (e.g., two concurrent quorum sessions), and no ordering/precedence rule is given for which one wins if both land in the certified prefix.

6. **No expiry handling for the authorization's own sequence limit (design gap, ln 97/168).** The authorization statement carries a signed "sequence limit," but the only described trigger for retiring reserved keys/canceling is a crash ("if it loses staged keys ... requires cancellation," ln 168). If the certified prefix simply advances past the sequence limit without anyone crashing (destination is alive but slow), it's unclear whether the authorization silently becomes unusable while its keys stay reserved indefinitely, or whether an explicit cancel is still required. `usedPublicKeys` reservation being permanent regardless (ln 109/113) means an unbounded number of "expired-but-never-cancelled" authorizations could accumulate reserved key material with no cleanup path described.

7. **Quorum composition for cancellation is not pinned down (source limitation, ln 113).** "The current voter set certifies it" — but the current voter set still includes the very seat whose device is unreachable (old human retains vote/command until activation, ln 103). Whether "current voter set certifies" means unanimity or some threshold isn't in this excerpt; if it's unanimity, cancellation could require a signature from the exact party who is unreachable, which is often the reason the transfer stalled in the first place. This looks like it depends on base-protocol quorum semantics not included here rather than being decidable from the excerpt.

### Recovered-human identity

8. **Identity of "the returning human" is established socially, not cryptographically (documented limitation, ln 97).** When the last certified human game key is lost, authentication reduces to "every current active human controller must approve the exact authorization statement." The design correctly forecloses cheaper spoofing vectors ("a device identity backup or recovered master never authenticates the returning human on its own"), but the fallback path has no cryptographic tie to the specific individual — it's entirely the existing quorum vouching for identity. That's a legitimate design choice for a trusted-group game, but it means the "recovered-human identity" guarantee is only as strong as the current quorum's judgment, not a protocol-level proof. Worth stating explicitly as an accepted trust boundary rather than leaving it implicit.

9. **Return quorum can shrink to a single approver (worth flagging, ln 97/103).** "Every current active human controller" as the approval set is correct and consistent with old-quorum certification elsewhere, but in a 4-human game where 3 seats have already gone through bot recovery, a *single* remaining human could unilaterally "approve" a return/re-key for another seat. This isn't a violation of stated quorum rules (it *is* literally the full current quorum), but it's a sharp edge worth surfacing: quorum size for this security-sensitive identity approval degrades silently as other seats recover to bots.

### Confirmed intact (per your constraints)
- No copied voting keys: ln 97 ("destination voting key must be generated on the destination device, independent of every original master"), ln 160 ("no source safety tuple is copied into the new signer") both hold as stated, and the constructor guards (indexed-db-protocol-journal.ts:101–105) reject a mismatched/copied binding.
- Strict quorum isn't weakened anywhere in the excerpt — every authorization/cancellation path routes through "current voter set"/"old quorum" certification; the only ambiguity is the *undefined threshold* (finding 7), not an actual relaxation.
