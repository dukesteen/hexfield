# Local passphrase lock review disposition

Claude reviewed the pinned source excerpts and design with tools and MCP disabled. The exact prompt, source bundle, source hashes and unedited response are in `local-encryption-review-{brief,input,manifest.sha256,raw}.md` (the manifest has a `.sha256` suffix). The design was revised **after** that snapshot; its hash in the manifest intentionally describes the reviewed version, not this disposition's revision. No vault implementation was made.

| Finding                                                     | Checked against pinned source                                                                                                                                                                                                                                                            | Disposition                                                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Promotion binding has incompatible plaintext/stored uses | Confirmed. `indexed-db-protocol-journal.ts` compares `staged.bindingBytes` to `keyBinding.bytes`, decodes those bytes, writes them as the new stored binding, and constructs a default `TransferImportStore`. `expectedActive.bindingBytes` serves both validation and stored CAS.       | **Blocker accepted.** The revised design requires separate plaintext and captured stored representations for both bindings, vault-aware stage injection, encryption before the transaction, stored-byte CAS and a post-promotion safety-write/reload test.                                                                                                           |
| 2. Random-nonce encryption breaks direct byte equality      | Confirmed in transfer stage/readiness retries and promotion's `canonicalEncode(staged)` comparison. Deletion parses public start, pointer, catalogue and tombstones inside a transaction.                                                                                                | **Blocker accepted.** Decrypt and compare outside IDB transactions, retain the exact ciphertext read for in-transaction CAS, and keep the named deletion inputs and transfer final tombstone public. Do not decrypt inside a transaction or use a deterministic nonce.                                                                                               |
| 3. Envelope overhead and escrow registry                    | The byte store and registry both cap records at 16 MiB; the registry contains public commitments, encrypted envelopes and irreversible status, and a missing registry means empty.                                                                                                       | **Accepted with refinement.** Explicitly allowlist the registry as public. Keep 16 MiB as the protected _plaintext_ cap and define a separate strict stored-envelope cap large enough for any previously legal record. A locked/corrupt protected read must throw, never become `null`. Test near-cap registry and private records.                                  |
| 4. Nested Web Lock deadlock                                 | This is a prospective risk, not a current vault defect: journal promotion already acquires a writer lease internally, while credential and escrow paths acquire ceremony locks. A queued exclusive vault request can block a nested shared request from an owner already holding shared. | **Accepted as implementation blocker.** Take one shared lease at the owner boundary before writer/ceremony locks, pass an asserted generation token to inner stores, and never reacquire the vault lock within that owner. Test queued exclusive migration against nested store work in tab and worker.                                                              |
| 5. Inserted keys between scan and migration                 | Direct IDB writers exist in journal and transfer import, so wrapping `IndexedDbByteStore` alone will not fence them. Comparing only scanned record values does not prove the key set stayed fixed.                                                                                       | **Accepted.** Compare the complete `bytes` key set inside the migration transaction, fence all direct writers through the owner lease and check generation during protected writes. Test concurrent insertion. The source database is currently v4; a proposed v5 `versionchange` may evict old connections, but does not itself fence later same-version rotations. |

Implementation should start only after the owner-level lease and plaintext/stored-byte contracts are specified together. In particular, a generic encrypted byte-store wrapper without the journal and transfer changes would risk a plaintext transfer binding or a permanently stuck promoted seat.
