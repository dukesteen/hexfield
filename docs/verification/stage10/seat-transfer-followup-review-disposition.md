# Seat-transfer follow-up review disposition

The [raw read-only review](seat-transfer-followup-review-raw.md) used the exact [excerpt bundle](seat-transfer-followup-review-input.md) and [pre-review source manifest](seat-transfer-followup-review-manifest.sha256). Claude had no tools. The first two CLI attempts with larger bundles produced no review; the final focused request returned the preserved raw text. No production code changed in this pass.

| Finding                                 | Disposition                                                                                                                                                                                                                                                                             |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1, alleged orphan safety record         | Rejected. `journalAbsent` in `IndexedDbProtocolJournal.load()` includes `consensusBytes`, which is the safety record. The later `loadSafety()` calls that same record `bytes`. The planned `promoteTransfer` transaction must still repeat this all-absent check internally.            |
| 2, multiple seats on one device         | Valid omission. The revised design explicitly supports one seated human per device per game and rejects an unrelated existing binding.                                                                                                                                                  |
| 3, lock order cannot be checked         | Current-source limitation. Game-wide active and authorization-scoped staging leases, their acquisition order, and the IndexedDB comparison are phase-two implementation work, not existing behavior.                                                                                    |
| 4, no cancel timeout                    | Deliberate strict-agreement policy. A current voter may propose cancellation whenever a destination is unresponsive; only the ordinary current quorum certifies it. No timer changes membership. This is now explicit.                                                                  |
| 5, cancel versus activation             | Clarified. Both require the exact pending ref and certified parent. One certified entry wins; replay clears pending, so the other is invalid. Concurrent proposals do not bypass agreement.                                                                                             |
| 6, authorization sequence limit         | Clarified. `validUntilSeq` bounds when the owner/approval statement may become a certified authorization. It does not expire a pending authorization; certified cancel or activation is required. Reserved keys stay reserved.                                                          |
| 7, cancellation quorum                  | The ordinary current voter threshold applies. In a two- or three-human game, losing a required voter can permanently pause cancellation and activation; the design already states that strict-agreement consequence.                                                                    |
| 8, fallback identity                    | Accepted trust boundary. If the last human game key is lost, every current active human signs an explicit approval for the exact destination. This is social identification by the surviving humans, not cryptographic proof from a master or device backup.                            |
| 9, one approver after repeated recovery | Rejected under the current recovery rule. From four humans, one recovery leaves three; another cannot satisfy the old three-voter quorum with only two remaining. Two- and three-human genesis games cannot recover a human. The revised design states the minimum three-approver rule. |

The remaining work is implementation, not a missing policy decision: define and test the new signer's fresh next-height safety record, the atomic promotion API and lock ordering, lawful custody evidence for a recovered return, and the certified route update. Until those paths exist, an imported save is read-only and no new key may sign.
