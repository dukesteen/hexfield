# Certified fresh-key resume from an imported full save

An HXFS1 import is a verified, read-only copy of one certified prefix. It contains historical consensus safety and may contain encrypted original masters and escrow shares, but it contains no transferable voting authority. Stage 10 requires a new controller key to be certified before another browser can play that seat. The shortest path reuses the existing live seat-transfer protocol and treats the imported file as a pinned history checkpoint, never as a source of signatures or private delivery.

## Existing boundaries

- `online-full-save-store.ts` writes imported bytes only under `online-full-import/v1`. `openOnlineFullSave` checks the content hash and revalidates the signed start, deck transcripts, every certificate and historical safety on each open. `online-full-save-worker.ts` returns a read-only display and never returns decrypted material to the UI.
- `online-transfer-bootstrap.ts` validates a source-supplied signed start and contiguous certified prefix without installing a journal. `OnlineTransferDestination` reserves fresh destination game/bot keys and an independent transfer-encryption secret, imports a lawful source's sealed packet, signs exact-parent readiness, and calls `IndexedDbProtocolJournal.promoteTransfer` only after certified activation. Promotion creates fresh next-height safety and rejects any active or partial journal on a fresh device.
- `transfer-membership.ts` requires destination device/game-key possession, a live current-owner game/device intent or the recovered-return approval rule, and an old-set commit certificate. The destination does not join the voter set at authorization. Its new keys become authoritative only after the activation certificate at the next height.
- The current `OnlineTransferLink` starts from a source-device-signed invitation and requires a signaling server origin. An imported file alone cannot locate a live peer, create that invitation, or use manual-only transfer signaling.

## Product flow

1. The importer opens a verified HXFS1 record and chooses **Request this seat on this device**. The screen explains that a current player must start and approve a transfer; importing the file cannot cast a vote. It displays the archive game ID, signed player names, seat, certified head and whether its private capsule is encrypted. No archived safety or private bytes leave the full-save worker.
2. A current active human opens the existing transfer control in their live game and sends its signed invitation to the importer. For a live human seat this must be its current owner. For a recovered bot's return, a lawful current human recoverer/host starts the return path. The importer opens the invitation and selects the archive ID. The invitation's game ID and genesis digest must equal the archive's verified start. The source and destination authenticate each other on the transfer-only channel; this does not expand the frozen gameplay roster.
3. The destination worker pins `{archiveId, attemptId, gameId, genesisDigest, seat, devicePeer}` durably before producing an offer. It loads HXFS1 by ID, validates it again, requires its historical safety seat to equal the requested seat, and compares its genesis entry and each imported certified entry's **entry hash** with the corresponding entry in the freshly received, fully verified source bootstrap. The bootstrap must extend the imported head. Different certificates for the same certified entry may be valid; different entries, gaps, a newer archive than the source, or a missing archive fail closed. The worker repeats this check on restart and on a refreshed bootstrap. The archive is a checkpoint, not a source of current membership or routes.
4. The destination generates or reloads one fresh device identity from its own storage and uses `prepareOnlineTransferCredentials` to reserve independent game, hosted-bot and transfer-encryption keys for the exact signed attempt scope. It sends only the public offer and possession signatures. It never imports the archived voting key, safety tuple, device identity or master as an approval. The source shows the selected destination and requires explicit confirmation before owner intent, submission or private delivery.
5. The current old voter set certifies `transfer-authorize`. The source sends its existing bounded signed and sealed private packet only after that certificate. The destination verifies source custody and the packet's exact authorization, then reconstructs every affected private seat through the latest certified parent. A private HXFS1 capsule is optional reference data and is **not** substituted for this authenticated packet. After durable staging, the destination signs readiness for the current parent. Parent advances require fresh replay/readiness, not a new unapproved key or rebased signature.
6. The old set certifies `transfer-activate`; the destination verifies the final contiguous prefix and atomically promotes its staged material under the game-wide writer lease. Only then does it open the existing online game with the new binding, fresh consensus safety and device routes derived from certified transfer state. It sends a verified receipt after promotion. The archived file stays in the import namespace and remains read-only.

The imported file can be stale and still be useful if its complete history is an exact prefix of the current certified log. It cannot overwrite a newer local journal. If the destination already has an active journal for this game, promotion uses the existing same-device retired-binding checks; another active seat or a partial journal is an error, never an instruction to replace that journal with the file.

## When no live owner is available

The historical safety key and optional original master do not authenticate the current human controller. In a live transfer, the current owner's game key or certified device route must sign owner intent, and the current old voter set must certify the change. A surviving quorum alone does not satisfy the live owner-intent rule. If the game has four humans and the owner is truly gone, the existing certified offline/recovery path may first replace that seat with a bot; a later `return` can use the last certified human game-key intent or unanimous current active-human approval as specified by `transfer-membership.ts`. It carries the full eligible affected bot set and still needs current certification, private custody, readiness and activation. Possession of an HXFS1 master never replaces those approvals.

With only two or three original humans, a missing required voter can leave the old set unable to certify recovery or transfer. The imported file remains read-only until the required voter returns. The same applies when the source cannot prove custody, current peers cannot establish a certified head, the quorum cannot certify, or a manual-only game has no supported transfer link. Do not offer an offline “restore authority” button in those states.

## Minimal implementation slices

1. **Worker-bound checkpoint.** Add an optional `importedArchiveId` to the destination transfer request and durable destination locator in `online-protocol-worker.ts`, `online-transfer-destination.ts` and their message schemas. A worker-only helper opens `online-full-import/v1` by ID, compares the verified archive prefix with every accepted source bootstrap, and returns a small public result `{gameId, genesisDigest, seat, importedHead, currentHead}`. Bind the archive ID immutably to the attempt; a missing or changed archive after reload stops readiness. Keep `OnlineTransferDestination`'s existing no-archive path unchanged.
2. **Entry point and source pairing.** Add a TanStack mutation for starting an import-bound destination from an existing signed transfer invitation. The imported-save screen presents the current source's URL/code input or uses the existing `/transfer/$code` route with an import ID selected before key reservation. The source game uses its current `OnlineTransferBrowser.openSource`, explicit destination selection and confirmation. Do not derive a source device from the archive's old route, and do not silently create a fresh live journal when a peer is absent.
3. **Acceptance.** Test a public-only imported file on a clean destination: signed matching prefix, one ordinary head advance, fresh key offer, owner approval, old-quorum authorization, sealed delivery, exact-parent readiness, certified activation and atomic promotion. Assert the archived safety tuple is not installed and the new game key differs from the archived controller. A locked or absent private capsule must neither authorize a transfer nor block a valid source-packet path. Add rejection tests for a divergent/stale-ahead archive, wrong game or device, no owner intent/quorum, partial local journal, and restart after staging or before promotion. A separate bounded recovered-return test covers the unanimous-current-human path. Native server-mode transfer completes the product check; manual-only import stays read-only until transfer-link support exists.

This plan adds no new membership variant or weaker quorum. The only new authority-sensitive step is the worker's immutable binding between an imported checkpoint and the already certified transfer attempt.
