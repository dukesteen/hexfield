The signed policy migration needs these corrections before implementation:

- `takeover.afterSeconds` is a bounded integer from 15 through 86400, default 120, or `never`. Canonicalize `never` to a single mode encoding. The honest timing gate reads the signed value. UI presets do not restrict the protocol range.
- Version 3 must identify a version 2 save before strict parsing of newly mandatory fields, so users see an explicit unsupported-version result. `validateGenesis` currently parses the full schema before its version check; lobby restore needs equivalent treatment.
- `genesis-identity.ts` constructs `genesisBody` from an explicit field list. The new policy must be included there, as well as in the signed lobby state, freeze agreement, genesis schema, and online-start equality check. Otherwise it is absent from genesis identity despite appearing in the body.
- Presence entries need their own schema and validator path. The current recovery membership dispatch treats every non-authorization change as activation, and replica submit logic assumes an authorization statement. Forbid presence entries while recovery is pending because activation checks bind the exact parent.
- The design text must distinguish current behavior from future policy: the current authorization validator does not require a certified offline marker; the proposed policy does. A still-online target is not eligible for policy takeover. A separate voluntary transfer would require its own design.
- Local monotonic absence observation and user approval govern newly signed votes only. Certified replay stays deterministic. Target contact cancels a local candidate before certification but cannot revoke a durable vote or certified authorization. Two- and three-human games still lack the old quorum after one departure.

The review packet did not independently verify all callers or transport identity assumptions. Before policy implementation, audit every recovery-change kind branch, the peer-ID to active-controller mapping, and restoration of already persisted consensus votes. The existing remote-proposer regression establishes only the uncontested signed-submit path; add the adversarial cases above rather than treating it as a complete takeover acceptance test.

## Follow-up implementation evidence

The current protocol-v2 recovery facade now addresses A1–A5 without adding the proposed signed policy or presence entries:

- A1: local recovery admissibility is checked before signing each new vote. An unapproved value becomes a nil prevote or precommit; the pre-persistence positive-vote assertion remains. A focused controller test forms a first-round polka and lock, then withdraws approval and verifies a round-two nil vote. Existing durable votes are unchanged and can retransmit.
- A2: for an initial authorization, the honest request and preview path requires the minimum certified active human seat other than the departed seat as host. It uses certified authority, not the locally observed online set. A valid amendment naming the certified pending authorization is exempt so a replacement host remains possible. Public certified-history validation is unchanged for deterministic replay and protocol-v2 compatibility. A signed noncanonical host fails local preview.
- A3: the session checks for a pending request before generating replacement keys. Its explicit request uses one serialized replica operation to approve and submit; a conflicting retained intent is rejected before approval mutation. A conflicting signed alternative cannot replace an existing approved intent.
- A4: target-return cancellation runs in the replica queue, clears candidate and uncommitted intent, cancels its timer, and resolves the waiting submit with `recovery-target-returned`. A queued approval invalidated by an explicit clear cannot later restore approval.
- A5: a valid signed amendment tied to the certified pending authorization receives a local preview and can be approved under the same exact-parent vote gate.
- A6: a stored readiness record for another bot level now returns the specific `recovery-bot-level-conflict` code. Stale-key deletion remains deferred as described above.
