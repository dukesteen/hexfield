# HX1 size and native connection check

The compact HX1 wire keeps the same signed `ManualCodeBody` and `p2p-manual-bootstrap` signature domain. It stores fixed-size keys, nonce, signature and offer hash as bytes. Its SDP encoder replaces exact, known Chrome data-channel lines with short tags and packs the origin, SHA-256 fingerprint and two common mDNS host-candidate fields. It writes every other line literally, including relay candidates and unknown attributes. Decoding restores the original SDP byte for byte before signature verification; the decoder also rejects alternate encodings of the same signed body. The [JSEP SDP rules](https://www.rfc-editor.org/rfc/rfc8829.html) and [ICE SDP rules](https://www.rfc-editor.org/rfc/rfc8839.html) informed the decision to retain negotiation attributes and all gathered candidates.

On 27 September 2026, two native headless Chrome tabs loaded the separate strict local server at `http://127.0.0.1:5295`. Each gathered two host candidates. The production-style aggregation read both `localDescription` and `icecandidate` events. Chrome repeats each candidate in the event with a matching `ufrag` extension; the aggregator now discards that event copy only when removing the redundant extension gives an exact candidate already in the SDP. It kept two distinct candidates per side. The signed offer was **434 characters** and the signed answer **520 characters**. Both decoded to their exact aggregated SDP, established a WebRTC data channel and exchanged `ping`/`pong`. The final browser run took 3.2 seconds. The previous native manual codes were about 1,144/1,099 characters; a same-machine pre-change size model with fresh random key, nonce and signature fields measured about 900/1,010 characters. Those baselines differ in network candidates, so they are context rather than a precise percentage improvement.

The `<700` target is met for this two-host-candidate case. A TURN or larger network candidate set may exceed it: unfamiliar candidate forms use literal encoding, and the existing 2,048-character limit rejects an oversized code instead of removing a candidate or SDP field. The test used native Chrome and a real data channel. A physical phone-camera QR scan remains unverified.

Focused validation: `manual-code.test.ts`, `manual-sdp-codec.test.ts` and `manual-bootstrap.test.ts`; p2p TypeScript build; scoped type-aware lint and format check. The native check used signed HX1 codes across the two browser tabs and printed only lengths, candidate counts and connection result, never SDP, identities or code contents.
