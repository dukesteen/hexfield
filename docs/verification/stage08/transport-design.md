# Stage 08 transport design

## Boundary and sequence

`@cp2p/protocol` already exports a synchronous `Transport` with `self`, `peers`, `send`, `broadcast`, `onMessage`, `onPeerChange`, and `disconnect`. `@cp2p/p2p` is currently a placeholder. Build one authenticated `PeerLink` first, then a `WebRtcTransport` that owns at most one live link per expected remote identity. Signaling adapters, the optional server, manual codes, mesh relay, settings, and UI follow this transport slice. The mesh manager must not report a peer online until its link has authenticated.

The first source slice owns `packages/p2p/package.json`, `src/signaling.ts`, `src/framing.ts`, `src/peer-link.ts`, `src/index.ts`, and focused `framing.test.ts` / `peer-link.test.ts`. It needs workspace dependencies on `@cp2p/codec` and `@cp2p/crypto`; `Transport` and `ProtocolClock` remain imported from `@cp2p/protocol`. Inject an RTC factory and clock so unit tests use fake connections and channels. No browser global is read at module import time.

## Negotiation and connection state

Create one `RTCPeerConnection` per remote peer and negotiated, ordered, reliable DataChannels `game` (id 0) and `bulk` (id 1) on both sides. The smaller `PeerId` is polite. Follow the [MDN perfect negotiation pattern](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Perfect_negotiation): set `makingOffer` before `setLocalDescription()`, use `isSettingRemoteAnswerPending` in the offer-collision test, let the polite side roll back and accept a colliding offer, and have the impolite side ignore that offer and its candidates. An adapter routes by sender and recipient; each bounded blob carries a connection generation and sender-local negotiation revision so late candidates cannot attach to a replacement or ignored offer. Trickle candidates when the adapter supports them; manual signaling waits for gathering completion with the documented cap.

Authentication is reset for a replacement `RTCPeerConnection`. A transient ICE `disconnected` state starts a five-second recovery timer; `failed` or `closed` reports the link down and asks the mesh manager to rebuild it. On a persistent disconnection call `restartIce()` through the same negotiation path. [MDN describes `disconnected` as transient](https://developer.mozilla.org/en-US/docs/Web/API/RTCIceTransport/state) and [documents that `restartIce()` schedules a restart offer, including after rollback](https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/restartIce). PING/PONG runs only after authentication, every two seconds; three missed replies mark the peer down. Clear all timers and queued bytes on disposal or link replacement.

## Identity and DTLS binding

Each link is created with an expected local `PeerId`, expected remote `PeerId`, identity signing key, and a required session scope. The scope is an application-provided lobby/invite identifier before genesis or the signed game identity after genesis. It is never taken solely from an unauthenticated signaling blob. On opening the `game` channel, each side sends a bounded `HELLO_INIT` containing a fresh 32-byte CSPRNG challenge. Once it has the other challenge and stable current SDP descriptions, it signs `HELLO` using the existing purpose-separated Ed25519 object signer. The signed body contains protocol version, scope, `from`, `to`, both challenges assigned to their respective peer IDs, and the same canonical DTLS fingerprint binding. A side authenticates only after the expected peer's valid signature echoes its _current_ local challenge and names the expected identities and scope. A reused RTC certificate or replayed old HELLO cannot satisfy a fresh challenge.

For the binding, parse fingerprints from `currentLocalDescription` and `currentRemoteDescription` only after negotiation reaches `stable`; pending `localDescription` or `remoteDescription` can represent a proposal that is not in use. [MDN explains this distinction](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Connectivity), and the [WebRTC specification defines the current-description properties](https://www.w3.org/TR/webrtc/). Select the sole active SCTP `m=application` section and its BUNDLE transport. A media-level `a=fingerprint` takes precedence over the session-level attribute; a missing, ambiguous, malformed, or conflicting value fails closed. Reject unsupported multiple active SCTP sections or multiple BUNDLE transports instead of guessing. Normalize algorithm names and colon-separated digest bytes, then hash a canonical structure keyed by sorted peer IDs: each peer ID maps to the fingerprint of its own current SDP. Both endpoints therefore sign the same binding despite reversing local and remote roles. [BUNDLE defines which media sections share a transport](https://www.rfc-editor.org/rfc/rfc8843.html); the SDP fingerprint attribute is specified by [RFC 4572](https://www.rfc-editor.org/rfc/rfc4572.html). The browser's DTLS handshake authenticates the certificate against the negotiated SDP fingerprint; the signed HELLO binds that fingerprint to the game's Ed25519 identity. Recheck the current binding after renegotiation; a changed fingerprint closes the link so the mesh manager rebuilds it with fresh challenges.

No application bytes or peer-up event pass the link before both challenges and signed HELLOs verify. Accept at most four unauthenticated control messages and 4 KiB total before closing; cap each HELLO at 2 KiB and the handshake at ten seconds. Unknown control types, application frames, invalid signatures, and wrong scopes before authentication close the link without forwarding data. These are connection-security failures, not game-protocol accusations. Signaling relays can delay or drop messages, but cannot substitute a DTLS identity without causing this check to fail.

## Framing and bounded flow control

Use binary frames on both channels with the same eight-byte header for every message: `msgId` u32, `index` u16, `count` u16, followed by up to 16 KiB minus eight bytes of payload. One-chunk messages use `count=1,index=0`, so no unframed/fragment ambiguity exists. Copy accepted caller bytes before queueing. Allocate IDs from one per-link sequence across both channels; a replacement link starts a new generation. The receiver keys partial and recently completed IDs by link generation and ID, rejects zero count, out-of-range index, inconsistent count, conflicting duplicate payload, oversized chunk, or a message that would exceed 1 MiB. Identical duplicates can be ignored. Keep at most eight partial messages and 2 MiB total partial bytes per link, expire them after 30 seconds, and retain a bounded recent-completion tombstone set to stop a duplicate complete message from being delivered twice. Emit one detached `Uint8Array` only when all chunks arrive. Exercise malformed frames before allocating the claimed count.

Use `bufferedAmountLowThreshold=256 KiB`; stop draining a channel while its `bufferedAmount` exceeds 1 MiB, resume on `bufferedamountlow`, and bound each channel's application queue. [MDN documents this notification and the negotiated-channel ID requirement](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Using_data_channels). `Transport.send` returns `void`: it means local admission into a bounded queue, not remote receipt. It throws synchronously if the peer is unauthenticated/down, the message exceeds 1 MiB, or the queue lacks room. Temporary DataChannel backpressure queues within the cap and is not peer misconduct. Once accepted, a later channel closure or `send()` failure clears queued data and reports peer loss; the protocol's certified-log sync/retry handles delivery uncertainty. Browsers may throw `InvalidStateError`, `OperationError`, or `TypeError` from `RTCDataChannel.send()`; handle these as local transport failures rather than invalid peer messages. [MDN lists those send failures](https://developer.mozilla.org/en-US/docs/Web/API/RTCDataChannel/send).

The current `Transport.send` has no priority argument. Its traffic uses `game`; an explicit later bulk-send extension can route snapshots and sync batches to `bulk` without inspecting opaque protocol bytes in the transport. The second channel is still created and tested in the first slice. This preserves the intended separation without silently changing protocol routing.

## Mesh integration and tests

`WebRtcTransport` owns the expected-roster map, one `PeerLink` generation per identity, and signaling subscriptions. `peers()` lists authenticated live links only. `send` and `broadcast` copy bytes and target those links only; `onMessage` tags bytes with the authenticated identity, never the signaling sender field. `disconnect` closes one link and emits one down transition. Later adapters provide manual non-trickle exchange, server trickle exchange, and signed in-mesh relay; the transport consumes their common bounded signaling interface. The optional signaling service forwards opaque blobs and never supplies peer authentication.

The first slice's fake-RTC test plan covers simultaneous offers, ignored-offer candidates, restart and stale generation, wrong expected identity, swapped SDP fingerprint, old signed HELLO with a reused certificate, missing/late HELLO, and no pre-auth delivery. Frame tests cover 0/16 KiB/1 MiB messages, both channels sharing IDs, out-of-order and duplicate chunks, conflicting duplicates, declared oversize, aggregate caps, 30-second expiry, input-buffer mutation, queue-full synchronous failure, and resume at the low-water event. The next slice adds a four-peer mesh integration test with an injected Node RTC implementation; browser coverage and manual QR flow remain later Stage 08 acceptance work.
