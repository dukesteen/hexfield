# Stage 08 mesh and signaling adapters

## Starting boundary

The first slice provides an injected, identity-bound `PeerLink`, bounded binary framing, and a `SignalBlob` carrying a sender-local connection generation and negotiation revision. It has fake-RTC coverage but no `Transport` implementation, deployed signaling route, or real browser connection. The next implementation should connect this link to the protocol's existing `Transport` without changing game-message authentication: the callback's `from` must always be the PeerLink's verified identity, never a field supplied by signaling.

## Slice 2: mesh manager and in-process signaling

Add `packages/p2p/src/web-rtc-transport.ts` and tests, plus a small in-process `SignalingAdapter` for integration tests. `WebRtcTransport` takes the local Ed25519 key, a required lobby/game scope, the expected peer roster, an RTC factory, `ProtocolClock`, ICE configuration, and a signaling adapter. Reject a local key that differs from `self`, duplicate roster identities, a roster larger than six, and attempts to connect to an unknown identity. One live `PeerLink` per remote peer owns each pair of negotiated channels. The manager creates a fresh local link generation on every rebuild, routes adapter signals only to the expected peer's link, and ignores obsolete generations. A `PeerLink` authentication callback moves the peer into `peers()` and emits one up event; closure removes it and emits one down event. `send`, `broadcast`, `onMessage`, `onPeerChange`, and `disconnect` implement `Transport` directly. Broadcast sends an independent copied payload to each authenticated link. `send` throws on a missing/down peer or full local queue; it makes no delivery promise after admission.

For initial connections, the lower `PeerId` offers first; perfect negotiation still resolves crossed explicit attempts. If both peers create replacement attempts, keep one deterministically selected attempt and close the other before emitting online. A fresh 128-bit attempt ID, in addition to the numeric PeerLink generation, identifies a particular offer/answer exchange across process restarts. Bind signaling to `{scope,from,to,attemptId,blob}` with an origin Ed25519 signature. Verify the signature against the expected roster identity before routing, cap envelope size, and drop stale or out-of-order attempts without marking the peer malicious. A per-peer bounded retired-ID set and the active attempt ID reject late replay during a process lifetime; the signed, fresh two-nonce HELLO remains the final DTLS identity and replay check across restarts. The adapter's `onSignal(from,blob)` value is only a routing hint until this envelope verifies.

The envelope deliberately has no wall-clock expiry. `ProtocolClock.now()` can be monotonic and is not comparable across peers, and even synchronized wall clocks can differ. Local timers only retire stalled attempts and schedule reconnects; they are resource cleanup, not authentication. A replayed old offer after a full process restart may briefly occupy a bounded pending slot, but it cannot pass the fresh HELLO challenge or expose application traffic. A server or manual-code adapter may additionally enforce its own wall-clock lifetime for operational cleanup, never as the sole freshness proof.

`Transport.send` currently has no bulk hint. Route normal protocol messages through `game`. Keep a separate explicit bulk operation on `WebRtcTransport` for later snapshot/sync integration; do not parse opaque protocol bytes in the transport to infer priority. The manager can expose read-only per-peer diagnostics from `RTCPeerConnection.getStats()` after this basic bridge is working.

Tests use four injected RTC peers and the in-process adapter to form all six pairwise links, deliver a payload through `Transport`, lose and rebuild one pair without duplicate up/down events, and reject an unknown or forged signaling origin. One test should use a real Node RTC implementation selected after a compatibility spike; fake-RTC tests alone cannot establish browser negotiation or ICE behavior. Keep application protocol history out of these tests until the transport itself passes.

## Slice 3: optional server route

Build a shared room core in `apps/signaling` and a Node `ws` host first; the Cloudflare Durable Object host uses the same validation, limits, and forwarding rules. On WebSocket open, the server gives a fresh challenge. `join` signs `{roomId,peerId,challenge,issuedAt}` so a recorded join cannot claim a later socket; the server verifies the Ed25519 key and bounds challenge age. The room core stores only peer-to-socket membership and last activity. It enforces eight peers, 64 KiB per message, 30 messages/s per connection, and a 24-hour idle TTL. A `signal` frame names a room member and forwards its opaque signed signaling envelope byte-for-byte. The server verifies sender membership and size/rate limits, but never parses SDP or game bytes and never logs blob contents. `leave` and socket close remove the mapping.

The browser server adapter connects to `wss://host/room/<roomId>`, signs join, routes `signal` to the mesh manager, and reconnects with bounded backoff. The room ID is an invitation locator, not a cryptographic identity; offer attempt ID, scope, origin signature, and final PeerLink HELLO supply that binding. Tests assert challenge replay refusal, membership/rate/size limits, exact opaque forwarding, no content logging, reconnect and stale-envelope handling. The Worker host follows once the Node host and adapter exercise the same room-core test suite.

## Slice 4: manual offer and in-mesh relay

Manual exchange is between inviter and each joiner only. Before encoding an offer or answer, wait for ICE gathering completion, capped at four seconds, and include candidates in the SDP. A single-use `HX1.` code contains a version, lobby scope, inviter/joiner identity, 128-bit attempt ID, expiry, minimally sufficient data-channel SDP, and an Ed25519 signature; the answer echoes the exact offer ID and scope. Canonical JSON, raw DEFLATE, and base64url produce the code. Reject wrong role, changed scope, answer for a consumed offer, expired code, signature mismatch, and SDP that loses DTLS fingerprint or ICE credentials. Code length under 700 characters is a measured target across real browser SDPs, not an invariant that can be asserted from a synthetic SDP alone. Copy/paste works before QR scanning or share UI is added.

After one direct PeerLink authenticates, it may carry a bounded `RELAY_SIGNAL` control message distinct from application game frames. The relay payload is the origin-signed envelope above with `to` an expected roster member and one-hop TTL. A forwarder may route it to another authenticated member but cannot change `from`, `to`, scope, attempt ID, or SDP without invalidating the signature. Only the target feeds the verified blob to its PeerLink; intermediate peers never report the origin online merely because they saw a relay. Cap per-origin pending envelopes and forwarding rate, suppress duplicates by signed envelope hash for a bounded window, and do not relay a relayed packet again. Tests connect four peers through inviter-only manual exchanges and then establish the remaining full-mesh links via relay; tampered origin and wrong-scope packets must not create links.

The settings panel, TURN credential query, QR camera path, connection diagnostics UI, and Chromium/Firefox/WebKit acceptance runs follow these network slices. They use the same `WebRtcTransport`; none should add a second identity or message-authentication path.
