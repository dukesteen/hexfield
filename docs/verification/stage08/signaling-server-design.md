# Stage 08 signaling server slice

The Node host and a later Cloudflare Durable Object host will call the same room core. The core owns connection challenges, authenticated membership, per-connection rate limits, room activity, and routing decisions. A host only accepts WebSockets, supplies bytes and a clock, and performs the core's send/close actions. It never logs a signaling envelope or SDP.

## Join and replay boundary

On opening `/room/<roomId>`, the server sends a fresh random 32-byte challenge tied to that socket and room. The client signs `{version:1, roomId, peerId, challenge}` under `p2p-room-join` with its Ed25519 identity key. The server checks the URL room, exact body shape, signature, one-time challenge, and a local 10-second join deadline before admitting the socket. It rejects a second join on the same connection and a duplicate live identity in the room. Replaying a join on another connection fails because that connection has a different challenge; replaying on the original connection fails because its challenge was consumed. No client timestamp or cross-device clock comparison is needed. The server may expire a pending challenge using its own monotonic clock.

The room ID is a 10-character lowercase base32 locator. It is not an identity credential. The signed origin envelope in each `signal` payload still binds `{scope,from,to,attemptId,sessionId,attemptSeq,blob}`, and `WebRtcTransport` verifies it before touching a `PeerLink`. The server authenticates the socket sender and routes an opaque envelope string; it does not verify, parse, modify, or log the inner SDP/candidate blob.

## Size and rate boundaries

The Stage 08 service limit is **65,536 UTF-8 bytes per complete WebSocket message**, including the outer JSON frame. The existing signaling-envelope validator permits up to 70,000 canonical bytes so that other adapters can carry larger envelopes; the server adapter deliberately accepts only the subset whose complete wire frame fits 65,536 bytes. It checks the byte count before send, and the Node host sets `ws` `maxPayload` to 65,536. Neither limit is raised. A rejected oversized signal produces a local send error; the mesh may retry through another signaling path.

Each connection may send at most 30 messages in a rolling one-second window, including join and signal frames. A room holds at most eight authenticated peers. Rooms and their sockets are removed 24 hours after last valid activity. Incoming binary, invalid UTF-8, malformed frame shapes, unauthenticated signals, wrong-room joins, or wrong recipients fail closed. Forwarded envelope text is byte-for-byte identical; only the small outer routing frame is reconstructed. The core exposes no content logging hook.

The Node host and browser client each cap their own WebSocket `bufferedAmount` plus the next UTF-8 frame at 256 KiB. A slow server recipient is disconnected; a full client buffer causes a local send failure, not an accusation against a peer. The client also closes and retries a socket that stays open without completing the challenge and membership acknowledgement within 10 seconds. A challenge is accepted only once per socket and must be canonical base64url encoding of 32 bytes.

The Node host uses `ws` with a pre-existing HTTP server, `noServer` upgrade handling, `maxPayload`, and compression disabled, following the [official ws API](https://github.com/websockets/ws/blob/master/doc/ws.md). The later Cloudflare host can use `DurableObjectState.acceptWebSocket` and `getWebSockets` for hibernation while keeping the same room decisions, as described in [Cloudflare's Durable Objects WebSocket documentation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) and [hibernation example](https://developers.cloudflare.com/durable-objects/examples/websocket-hibernation-server/). The DO host will need a persisted challenge/session attachment design across hibernation; this slice does not claim that adapter exists.
