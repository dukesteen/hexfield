## Review findings (cheat-capture path)

**1. `cheatCandidateId` collision can silently drop distinct, still-valid evidence (correctness)**
`cheat-candidates.ts:33-35` defines `cheatCandidateId = cheat/${seat}/${kind}` — it depends only on seat + evidence kind, not on the artifact or the certified parent (`at`). In `replicated-log.ts` `rememberCheatClaim` (~2983-3000), the order is: check `crypto.cheats` for an already-*certified* finding → check `this.cheatCandidates.has(id)` → capacity → **then** `verifiedCheatClaim`. Failure sequence: seat S sends a bad proof of kind K at head H1; it verifies and is stored under `cheat/S/K` but has not yet been committed as a certified finding (e.g. still waiting on quorum/proposal). Before that happens, S produces a second, different bad proof of the same kind K at a later head H2. `has(id)` is already true, so the second claim returns `success(undefined)` **without ever calling `verifiedCheatClaim`** — it is neither stored nor gossiped. If the first candidate never reaches finality (proposer stalls, historical-context eviction via `MAX_HISTORICAL_CONTEXTS`, etc.), the second, otherwise-provable cheat is lost with no retry path. The shown beacon-replica test only re-injects the *identical* bad message (idempotency), so it doesn't cover this case — it doesn't establish that distinct same-kind evidence is handled.

**2. CHEAT_CLAIM early auth gate is now scoped to `at.seq === head.seq` only (needs confirmation of what follows)**
The diff changes the pre-check in the `CHEAT_CLAIM` case from an unconditional `authenticatedCheatSigner` check to one gated by `message.claim.evidence.at.seq === this.context.log.head.seq`. For historical/future-seq claims, this cheap gate is now skipped entirely — correct in that historical claims need the historical authority/epoch (which `verifyHistoricalCheat` in `replay.ts:99-149` supplies), but it also means any peer can get a claim with a mismatched `at.seq` past this checkpoint with zero authentication. The excerpt doesn't show what code runs immediately after this check (before `rememberCheatClaim`/`verifiedCheatClaim` is reached), so it doesn't establish whether that intervening path is itself cheap/bounded for the unauthenticated, mismatched-seq case. Worth confirming, not assumed to be a bug.

**3. Capture work occupies the receive-queue slot for its full duration (bounded, but adds latency under adversarial bursts)**
`replicated-log.ts` ~1003-1010: `captureRejectedProofs` runs *inside* the same enqueued task as `receive()`, and `this.queuedMessages -= 1` / per-peer decrement only happen in the `.then()` after that whole async callback (including capture) resolves. So each non-fatally-rejected message from a voter holds its queue slot for hashing + strict re-decode + up to `verifyCheatProof` for up to 6 (beacon-v1) or 5 (deck-unlock) extracted candidates, rather than releasing the slot immediately on `receive()` failure. This is capped per peer per window by `admitExpensiveRequest(..., 'cheat')` (shares the default `EXPENSIVE_REQUESTS_PER_WINDOW`), so it isn't unbounded, but worst-case per-window cost is `EXPENSIVE_REQUESTS_PER_WINDOW × voters × up-to-6 verifications`, held directly in the path that also processes legitimate commands. Whether that's acceptable depends on the actual constant values, which aren't in the excerpt.

**4. `captureCertifiedDelivery` can trigger `offerAvailableInput()` twice back-to-back (likely benign, unconfirmed)**
`rememberCheatClaim` ends with `return this.offerAvailableInput();` whenever a new candidate is freshly stored. Both call sites that invoke `captureCertifiedDelivery()` (post-COMMIT enqueue, and the resume/recovery paths) then call `this.offerAvailableInput()` again immediately afterward in the same enqueued callback. Not shown to be harmful (sequential, awaited, not recursive/concurrent), but it's a redundant second call whose idempotency isn't established by these excerpts — flagging in case `offerAvailableInput` has any non-idempotent side effect not visible here.

**What the excerpts *do* support (no finding, for context):**
- Seat attribution for `false-steal-dispute`/`bad-steal-delivery` is enforced by the final `offender !== claim.seat → unproven()` check in `cheat-proof.ts` (~line 375), so even if a candidate were mis-tagged at capture time, the objective verifier can't attribute it to the wrong seat.
- `verifyCheatProof`'s header guard (`evidence.at.seq/hash` vs. `context.head`, plus `stateHash`/invariant checks) independently re-binds every claim to its certified parent regardless of caller behavior.
- Durable retention (`store.putIfAbsent`) strictly precedes `this.broadcast` in `rememberCheatClaim`, and `recoverCheatCandidates` re-runs `verifiedCheatClaim` on every record loaded at restart rather than trusting stored bytes — both match the stated requirements.
- Wire/queue bounds (`MAX_MESSAGE_BYTES`, `signedList maxLength(6)`, `unlocks maxLength(5)`, `MAX_QUEUED_MESSAGES_PER_PEER/TOTAL`) are exercised by the cited tests and appear to hold for the paths shown.
