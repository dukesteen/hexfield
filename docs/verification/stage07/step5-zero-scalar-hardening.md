# Zero-value commitment timing

`scalePoint` previously returned immediately for scalar zero because Noble's constant-time `multiply` rejects zero. Hidden hand counts, one-hot bits, and range bits can legitimately be zero, so a prover's Pedersen commitment work depended on those private values. This patch keeps `scalePoint` unchanged for other protocols and changes only Pedersen commitments.

For any canonical scalar `s`, `zeroSafeProductTerms` computes two nonzero Noble multiples with `q = (s >> 1) + 1` and `r = 2 - (s & 1)`. Their difference is `2qP - rP = sP`, including `s = 0` and `s = order - 1`. `pedersenCommit` combines the positive G and H terms before subtracting either correction. That avoids an identity intermediate for a zero count or blinding except at a public identity output. Bit proof preparation also computes `target - G` for both bit values before selecting the false target.

This equalizes the number of group operations in these call sites for every valid scalar and preserves the encoded commitment and proof bytes. It does **not** make browser JavaScript constant time. Noble's wNAF table choices, BigInt arithmetic, JIT behavior, and proof control flow can still depend on secrets. The [initial source review](step5-zero-scalar-review-raw.md) found the identity intermediate and conditional subtraction; the [follow-up](step5-zero-scalar-followup-raw.md) confirmed those fixes and recorded the residual limits. The final code also removes redundant scalar-to-byte conversions before the helper's canonical validation, since their work varied with scalar magnitude.

The focused crypto and protocol checks passed 65/65. They cover scalar boundaries, zero counts and bits, genuine signed steal delivery, and the pinned eight-type proof digest `b1e86a98ef84995fee4601548728a63045e165d999447a77fd1fd7b201eb573a`. The crypto build, type-aware lint, formatting, and diff checks passed. The [final source manifest](step5-zero-scalar-final-manifest.sha256) separates this patch from the committed public-arithmetic checkpoint.

One fresh, headed Chrome 153 run on strict port 5294 measured the final eight-type proof with the page visible and focused. Three independent full prove-plus-verify samples were valid and took 270.5, 232.8, and 209.3 ms. The [raw timing](step5-zero-scalar-headed-timing.json) records proving and verification separately. This is one machine's result below 300 ms, not a cross-device guarantee. A Node 22 full-proof diagnostic on an earlier version of this patch took 621.5, 555.2, and 570.0 ms combined; those numbers are not browser acceptance evidence.
