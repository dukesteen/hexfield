# Recovery void implementation review disposition

The [raw source-only review](recovery-void-implementation-review-raw.md) used the [pinned source excerpts](recovery-void-implementation-review-input.md) and [SHA-256 manifest](recovery-void-implementation-review-manifest.sha256). Claude ran with built-in tools and MCP disabled. The raw response is unchanged. The corrections below followed that pinned snapshot.

1. **Wrong local secret or unauthenticated share:** The review lacked `recovery-release.ts`. `recoverAuthorizedMaster` calls `openRecoveryRelease` for every original holder. That path verifies the certified release binding, current holder signature, sealed ciphertext proof, recipient seat and derived recipient encryption key, each escrow share opening, the exact original holder index set, and the recovered scalar against signed `masterPub`. A wrong recipient secret returns `recovery-release-recipient` before a void write. The focused test now asserts this. No code change was needed for this finding.
2. **Stale checks striking honest peers:** Confirmed and fixed. Both activation and void receivers now discard a check for another certified parent or authorization before admission and strike logic. A current-scope invalid signature still fails authentication.
3. **Opposite outcomes in separate durable slots:** Confirmed and fixed. Activation and void checks now occupy the same immutable `recovery-check` key per game, authorization, parent, and seat. The participant decodes either exact schema on restart. The focused test verifies an occupied slot rejects void signing and a durable void check can be retransmitted after participant restart.
4. **Post-void network output:** `schedulePrivateTimeout` already clears the timer and requires `status.kind === 'running'`. The master-reveal coordinator and audit already require an engine result, which void leaves null. Explicit void guards were added to direct proposal and master-reveal preparation methods for defense in depth. The session reports `void` separately from `complete`.
5. **Stale-entry classification:** Confirmed and fixed. `validateNextEntry` reports `stale-entry` or `missing-ancestor` first, then `game-void` for the next possible certified height.

The certified void remains a unanimous current-recoverer decision, not independently recomputable public proof of a derived-key mismatch or a public dealer-cheating finding. It carries no master, scalar hash, or `CHEAT_PROOF`. The engine winner remains unset. Worker and UI presentation are separate integration work.
