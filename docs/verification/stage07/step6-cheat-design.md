# Stage 07 Step 6: objective cheat records

The pure classifier, certified `cheat-proof` entry, and durable `CHEAT_CLAIM` delivery are implemented. Automatic capture of rejected artifacts, session/UI fairness presentation, and an `invalid-crypto` sequencer accusation remain open. A normal rejection alone is not a finding: the classifier must authenticate the owner's signed artifact at its replayed certified parent.

## Certified record

Use a protocol-only payload, not an engine input:

```ts
{
  kind: 'cheat-proof',
  claim: { seat, evidence: CheatEvidence }
}
```

The log validator intercepts this exact shape before `engine.apply`. It calls `verifyCheatProof(claim, historicalParent)`, checks the claimed seat, and requires `entry.stateHash` to equal the certified parent state hash. The resulting `ValidatedEntry` has `input: null`, no engine events, the same engine state, hand commitments and command nonces, and a new certified log head. The immutable entry carries the full signed evidence. `CryptoContext.cheats` keeps the first finding per `(seat, kind)`; with at most six seats and eight enumerated kinds it has at most 48 records. It is replay-derived and included in snapshot hashing. `evidenceId` is a domain-separated hash of the exact evidence. A second entry for the same seat and kind is rejected. The summary is for UI and result flags, never an authority for validating evidence.

`CheatEvidence.at` names the **parent where the attempted artifact was current**, not the later `cheat-proof` entry parent. The caller must reconstruct that certified prefix (as the existing Stage 06 historical accusation resolver does) and pass its `LogContext` to the pure verifier. The verifier checks the exact `(seq, entryHash)` and public state hash. A peer-supplied operation or hand ledger is never accepted as an alternative to this replay. Historical replay validates and hashes `CryptoContext`, including its frozen beacon, deck, count and steal operations. This permits evidence to be certified after another legal input has advanced the head without misclassifying it as stale. An artifact signed for a different operation, epoch, nonce or parent remains unproven.

Historical resolution checks the claimed parent hash against certified ancestry and authenticates the artifact under its genesis signer and domain before replay. A replay invocation shares successful findings from its own certified ancestry with nested parent replays, so prior cheat entries do not cause exponential recursive verification; the cache contains only certified findings and is capped by the first-finding limit. `ReplicatedLog.create` calls `restore`, which uses `replayCertifiedPrefix` even for an empty journal. Its returned `entries` array is the same array captured by the historical resolver and later appended by `persistCommit`, so live and restored peers have the same available certified ancestry. A focused live/restore test verifies this path with a later historical claim. `initialProposalContext` alone does not provide historical resolution and must not be installed directly as an active replica context.

## Evidence and attribution

The evidence union is `command-proof`, `beacon-reveal`, `deck-pass`, `deck-unlock`, `count-proof`, `steal-contribution`, `bad-steal-delivery`, and `false-steal-dispute`. Its artifact is a bounded canonical outer `{body, sig}` envelope with an unknown inner body. This is deliberate: a signer can sign a malformed inner proof. First authenticate the exact canonical body under its protocol domain and the public key derived from the certified operation. Check the expected seat, operation ID, actor order, parent, and any prefix before classifying proof failure. An unparseable outer envelope, wrong signature, wrong operation, stale context or invalid engine command never proves cheating.

- A command must be signed by its genesis seat, name the current head and an unapplied nonce, and pass engine validation and application. Derive hand and card obligations with `planHandTransition`; reuse `readCommandProofs` and `validateCommandForEntry` with only built-in proof checks. Only missing, malformed, wrong-count or invalid required proof results qualify. Business-rule failure, state-invariant failure, optional application policy failure, or unexpected evidence on a proof-free command does not. The signed command is self-contained once its certified parent is replayed.
- A beacon reveal uses the active frozen operation and `verifyBeaconReveal`. A signed wrong hash-chain link qualifies; a wrong seat, index or operation does not. Beacon extensions commit a new tip but have no comparable proof of the next tip, so they are not currently a cheat kind.
- A deck unlock includes its signed, validated earlier unlock prefix; `verifyDeckUnlock` checks the next actor and DLEQ. A wrong DLEQ or a malformed nested DLEQ after the remaining signed fields are checked qualifies. A deck setup pass is checked with `applyDeckPass` only when its hash equals the next pass hash in signed genesis. With a fully verified genesis, a bad committed pass should be unreachable; a differently signed pass is not proof of a bad committed pass.
- Count and steal contributions use the frozen pending operation and their existing verifiers. An authenticated invalid Schnorr/ephemeral/transfer proof qualifies, including malformed nested proof fields when all routing and non-proof fields are canonical. Wrong operation, seat, remaining-victim status or signature does not.
- A **bad delivery** is already proven by a certified signed steal dispute. The cheat evidence must exactly match the dispute stored in the replayed steal state and pass `verifyStealDispute`; this attributes the victim without publishing another opening. A **false dispute** qualifies only when `verifyStealDispute` reaches `steal-good-delivery`: the signed binding and DLEQ have authenticated a shared point that opens the fixed transfer correctly. Other dispute failures are not evidence against the thief. The fixed contribution is rechecked first.

The classifier returns `cheat-unproven` for any ambiguous case. It does not use a raw network rejection code as an accusation. In particular, a signed message from another operation can be invalid at the current head while remaining honest at its original head. The standalone function assumes the caller supplies a certified replay context; its current state-hash and anchor checks are defense in depth, not a replacement for certificate replay.

## Integration status

The protocol-only `cheat-proof` payload is admitted, voted, replayed, and included in snapshots without an engine input. `proposal.ts` and `replay.ts` reconstruct historical certified parents; the resolver first checks the certified parent hash and authenticates the genesis signer. `ReplicatedLog` retains the same certified ancestry array through live commits and restore. A test cites a newly committed seq-2 deck pass before and after its commit to exercise that live resolver.

The wire message is `CHEAT_CLAIM`, not `CHEAT_PROOF`. Verified replicas require a `CheatCandidateStore` before journal initialization. A claim is objectively verified and written to that auxiliary store before gossip or proposal. One candidate per `(seat, kind)` and at most 48 are retained; the first durable valid local candidate wins a race, while consensus decides the first certified finding. A failed write cannot gossip or propose. Restore quarantines malformed, future, or unverifiable auxiliary records and reports a status; a gossip transport failure cannot stop voting. One retained claim is retried at restore and one per pulse in rotating ID order. Gossip and historical cheat proposals have separate per-peer work budgets. A certified finding removes its pending candidate after the journal commit. The candidate has proposal priority while `prepareDeck`, `prepareCount`, `prepareSteal`, and `prepareBeacon` continue to prepare and retransmit owed contributions.

Historical parent verification still replays a certified prefix synchronously on a cache miss. The 16-parent cache, first-finding bound, cheap signer/hash checks, and per-peer work budgets bound ordinary receive work; an incremental replay job is not implemented. A stuck auxiliary store deletion could delay the serialized commit path, so durable store implementations should complete operations promptly.

Remaining Step 6 work is automatic capture of objectively bad signed artifacts in the `SUBMIT` and crypto contribution paths, an `invalid-crypto` signed-proposal accusation that preserves Stage 06 quorum rules, and replay-derived fairness findings/input count in `P2PSession` and the UI. Local exceptions, unsigned malformed messages, stale operations, invalid business rules, and rejected policy callbacks remain ordinary errors. The compact certified summary records one finding per seat and kind; further attempts are not separately certified.
