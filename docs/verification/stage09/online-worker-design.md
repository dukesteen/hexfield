# Online certified-context worker design

## Contract and boundary

[Stage 07, "Certified context and execution"](../../07-fair-randomness-hidden-info.md#certified-context-and-execution) requires the online protocol, engine and crypto to run together in a dedicated worker. Today `OnlineStartup` constructs `OnlineCeremony` on the main thread and `openOnlineGame()` constructs `VerifiedSessionDriver` and `P2PSession` there. The separate audit worker only moves the final audit. The smallest complete migration is one dedicated worker per online room from the frozen ceremony through live play. It owns ceremony material, signed setup, genesis admission, the certified log, private driver, bots, recovery, the journal and its writer lease. It keeps the existing separate audit worker for post-result replay. The main thread owns WebRTC/signaling/manual codes, room presentation and the Zustand-facing session proxy.

This boundary starts when a signed lobby freeze is offered to the ceremony. `LobbyController`, pre-game roster management, chat and device-link authentication can remain on the main thread: they are not the certified game state machine. The worker must independently verify the full freeze agreement and every subsequent artifact; no main-thread `verified` boolean or parsed genesis is authority. This leaves device-key crypto in `WebRtcTransport`, lobby and chat on the main thread. If the requirement is interpreted as _all_ online cryptography, including link authentication and chat, those modules need a later async-signer/transport redesign. Moving only `P2PSession` would not satisfy the setup portion of Stage 07.

| Current responsibility                                                                               | Worker boundary                                                                                                                                                                                                                                                                                              |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `OnlineRoom`: WebRTC, server/manual/mesh signaling, pre-game roster, lobby and chat                  | Remains main-thread. It forwards authenticated device-peer bytes and peer changes on a bounded port, without interpreting certified claims. It blocks output on close or authenticated dispute.                                                                                                              |
| `OnlineStartup`: freeze pin, ceremony, material, saved-record verification and activation            | Keep a small UI coordinator on main; move durable consent checks, `prepareCeremonyMaterial`/`loadCeremonyMaterial`, `OnlineCeremony`, complete saved-record admission and activation into the worker. Main obtains the freeze pin before its own ACK and freezes the device roster after the full agreement. |
| `openOnlineGame`: genesis checks, device-to-game projection, journal, driver, bot, recovery, session | Runs inside the same worker. Construct `createOnlineGameTransport` over the port-backed device transport so certified `onlineStart` determines routing there.                                                                                                                                                |
| `P2PSession`/`ReplicatedLog` and `IndexedDbProtocolJournal`                                          | Stay together in the worker. Worker acquires and holds the existing game writer lease before create/restore, and owns the IndexedDB byte-store connection used by outboxes and recovery.                                                                                                                     |
| Audit worker                                                                                         | Remains a separate disposable worker, spawned by the protocol worker if the target browsers and Vite build support nested workers. Its result is checked against the unchanged certified head before publication.                                                                                            |

[Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API) and [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Functions_and_classes_available_to_workers) are available in dedicated workers. The implementation still needs a browser capability check and a fail-closed error when either API is unavailable; it must not fall back to an unleased signer.

## Port contract and authority

Use a versioned, discriminated `MessagePort` protocol in new `apps/web/src/session/online-worker-messages.ts`, with runtime schemas and exact byte limits. Main-to-worker requests carry a room generation, request ID, operation and detached data. Worker-to-main responses carry that generation and request ID. Ignore late responses after close or a replacement worker. Do not send `Engine`, `Transport`, callbacks, `ProtocolJournal` objects, `AbortSignal`, voting keys, masters or commitment blindings through structured clone. The local human's exact hand and card identities cross only in the private-view message needed for display.

The initial request set is `pinFreeze`, `startCeremony(agreement)`, `resumePreflight(gameId)`, `attachDeviceTransport(self, peers)`, `validate(head, seat, command)`, `submit(head, seat, command)`, `showPrivate(seat)`, `hidePrivate`, `exportHistory`, `retryAudit`, recovery actions and `shutdown`. Transport events use `deviceFrame(from, bytes)` and `peerChange(peer, online)`. The worker emits `sendDeviceFrame`, `disconnectDevicePeer`, `startupProgress`, `sessionSnapshot`, `privateView`, `halted` and request results. Only `resumePreflight` may run before the main device transport exists. Its public invite and roster are still rechecked when `attachDeviceTransport` binds the authenticated local peer. The worker keeps an ordered peer snapshot so `Transport.peers()` remains synchronous inside the protocol.

The main transport adapter forwards `{fromDevicePeer, bytes}` and `{devicePeer, online}` in order on one port. `fromDevicePeer` comes only from `WebRtcTransport`'s authenticated callback; the worker nevertheless verifies message signatures, roster, operation context and proof itself. The worker's `Transport.send()` may synchronously reject a closed, unknown or oversized destination and then enqueue a port message. A successful enqueue means local handoff, not remote delivery. Main-thread send failures are returned as diagnostics; durable protocol outboxes and exact retries remain responsible for delivery. Bot seats never appear as device routes. The worker performs the certified game-key mapping and CP2G/genesis-digest framing, rather than accepting a main-thread routing claim.

The worker creates its own monotonic `ProtocolClock` from worker timers and `performance.now()`. Main does not supply current time in a message or act as the heartbeat scheduler. Tests can inject a fake clock into the worker runtime, as they do for the current protocol objects.

Add admission counters on both sides of the port. Device frames are at most the existing WebRTC frame maximum; gameplay remains at `@cp2p/protocol`'s 256 KiB payload cap. A starting bound is eight inbound frames per peer, 32 total, and 8 MiB total queued bytes, with one acknowledgement only after the worker has admitted or rejected each frame. Reserve a small separate control budget for close and peer-state notifications so a proof flood cannot delay cancellation. Bound UI/RPC requests (for example, 16 pending and 1 MiB aggregate payload) and outgoing bytes as well. These are proposed bounds, not measured throughput targets; verify ceremony retransmission behavior before treating any dropped frame as harmless. The existing `ReplicatedLog` limit of eight messages per peer and 32 total still applies after the bridge, but cannot bound already queued `postMessage` data on the main side.

The worker performs cheap length/schema/context/signature checks before expensive group work. Verification and the commit decision remain synchronous within its serialized protocol transition. One large synchronous proof can still delay a heartbeat even with a bounded queue; instrument real Chromium-worker proof duration and heartbeat delay. If an admitted proof exceeds the heartbeat budget, split that verifier into bounded work slices while retaining its state and final decision inside the protocol worker. Moving the present synchronous call into a worker alone does not establish the Stage 07 starvation requirement. No duration claim in this design is measured.

## Session proxy and UI validation

`P2PSession.subscribe()` publishes persisted certified effects. The worker sends a detached, versioned view containing the exact `{seq, headHash}`, projected public state, events, pending inputs, timers, status, audit/recovery summaries and the local human's legal-command set. It must never send bot signing keys, masters, blindings, recovered private seats or the driver's internal state. A separate requested private-view update may contain only the locally owned human seat's display fields, currently `seat`, `hand` and card `slots`; do not copy arbitrary `PrivateState.ext` into the UI. Tie this reply to the same head, room generation and visibility-request token. On conceal, dispute, worker failure and close, the proxy clears that cache and invalidates the token so a late reply cannot reveal an old hand. At the terminal result, use the audit report for other seats' hidden victory points; the current store's `getPrivate()` loop must no longer query hosted bots.

`OnlineGame.session` becomes a `GameSession`-compatible proxy for synchronous reads from its last complete worker snapshot. Install each snapshot atomically before notifying `attachSession()`/Zustand, discard older heads/generations, and make every returned object detached or immutable. When a private-view reply arrives for the current head, the proxy emits another update at that revision so `attachSession()` can refresh its synchronous `getPrivate()` read. `submit()` is an RPC carrying seat, command and both expected sequence and head hash. The worker compares those against its current certified context, runs `P2PSession.validate()`/proof preparation and signs only there. After any asynchronous proof preparation, it rechecks the head before signing. A response records whether the worker merely admitted a command or a later certified snapshot committed it; main must not infer a commit from RPC success. A matching UI cache is never evidence of validity.

Exact `validate()` cannot remain synchronous for online play: `GameActions`, `GameReadOnly`, discard/steal/development dialogs and trade forms call it during render, while exact validation needs worker-owned private and engine state. A main-thread engine mirror or a guessed result from legal templates would violate the boundary. Change the shared method to `validate(...): Result<void> | Promise<Result<void>>`; local sessions keep their synchronous result. The online proxy sends an advisory validation request keyed by room generation, head hash, seat and canonical command. Form controls use a small `checking | valid | invalid` result cache instead of calling `validate()` in render, and discard responses for older heads or edited commands. `submit()` always revalidates in the worker. The online export button must await worker `exportSave()`; the shared contract can return `Save | Promise<Save>`, leaving the typed `LocalSession` and its synchronous save coordinator unchanged. `retryAudit()` and recovery approval can be RPCs, with worker-issued results reflected in later snapshots.

## Open, resume and shutdown order

For a fresh room, main opens device links and the lobby as today. Before a freeze ACK it asks the worker to durably pin the exact freeze hash; main ACKs only after that succeeds. Once every human ACK has formed the agreement, main freezes the human device roster before the ceremony sends secrets. Worker verifies the full agreement, pins it, loads the existing device identity from IndexedDB and checks it matches the authenticated transport self, then generates and durably pins fresh owned ceremony material. It starts `OnlineCeremony` over the port-backed transport. It saves the signed start record before activating gameplay. After fully validating genesis and projection, it acquires its exclusive game writer lease, opens the bound journal and restores or initializes as current `openOnlineGame()` does. Only a worker `ready` result backed by that journal may expose a playable proxy. No key bytes or master secret need to cross the port: the worker loads device identity and owned material from the same origin's durable store. The main transport still retains its separate device key for link authentication.

On resume, the worker first loads and fully validates the saved record, signed freeze, certified genesis, transcripts and consent pins. It returns only the public invite and frozen device roster needed for `OnlineRoom` to reconnect; main must not derive authority from a cheap catalogue pointer. After the transport attaches, the worker uses load-only ceremony material, restores the exact saved result, checks the durable disclosure registry and flushes inbound disclosure messages before opening the bound journal. It opens the journal in restore-only mode. A wholly absent built-in journal may take the existing atomic first-initialization path only under the writer lease and exact saved pins. A missing binding, partial journal or changed genesis fails closed. Worker restart after failure repeats this durable path, never imports a main-thread state snapshot or generates replacement voting keys.

On an explicit close, main disables the game port's network output synchronously. If the worker detects authenticated post-consent disclosure, it stops its own output before reporting `halted`; main blocks the bridge as soon as it receives that report. Worker cancels pending preparation/audit, disposes ceremony and session, drains `ReplicatedLog.flush()`, closes journal/store and releases its game writer lease. Main then closes shared transport, device identity and room lease in the current `OnlineRoom.close()` order. A forced termination is the last resort after a bounded shutdown deadline; it must leave the journal as the only restart authority and report an error, not mark an unflushed command committed. Worker crash similarly disables output and clears proxy private data before a fresh worker may reacquire the lock. Shutdown/restart must be generation-fenced so an old worker cannot publish a late board or send packet into the new session.

`GameWriterLease` now provides an optional synchronous `onLost` callback and fences queued work when the held lock ends unexpectedly. Eleven focused storage tests cover loss, close-time draining and normal release. The worker integration must still use this callback to block outbound packets, dispose the session and surface an error. `P2PSession` handles network and timer callbacks outside `lease.run()`, so the lease helper alone does not stop an active signer.

## Implementation sequence and files

1. Add `online-worker-messages.ts`, a bounded device-byte bridge and worker/proxy contract tests in `apps/web/src/session/`. Wire the implemented immediate lock-loss notification from `packages/storage/src/game-writer.ts`. Keep the current main-thread path for comparison until the new path is complete. Add message generation, request IDs, exact-head checks, byte caps and cancellation first.
2. Extract worker-safe ceremony/game orchestration from `online-startup.ts` and `online-game.ts` into `online-protocol-worker.ts` plus a worker-owned runtime module. Move the record's full admission from `online-game-records.ts` into a worker-callable pure function; keep only cheap list/pointer metadata on main. Ensure `online-credentials.ts`, `IndexedDbByteStore`, `IndexedDbProtocolJournal`, `VerifiedSessionDriver`, `RandomBot` and audit job work in the worker build. Retain their existing cryptographic validators, not new callback approval paths.
3. Replace the online `GameSession` surface with a snapshot-backed proxy. Update `session-types.ts`, `session-store.ts`, `GameActions.tsx`, `GameReadOnly.tsx`, the dialog/trade form contracts and `OnlineGameScreen.tsx` for async advisory validation and export. Keep local play behavior and its synchronous save path intact.
4. Wire `OnlineRoom`/`OnlineStartup` to create and close one worker, bridge only the authenticated device transport, and preserve current freeze, dispute, retry and resume ordering. Remove main-thread ceremony/game instantiation once worker acceptance passes; never run two active signers for one device/game.
5. Add browser-backed acceptance for real freeze → ceremony → first certified action, terminal audit, close/reopen, writer contention and a killed worker. Then measure proof and heartbeat latency in Chromium workers and tune the proposed queue limits. Run dependency/static checks and focused tests before a broader suite.

Tests must cover wrong-game/device frames, a forged main-thread `verified` claim, malformed/oversized port messages, a peer flood while a valid vote waits, stale validation and submit responses after head change, hosted-bot private-state isolation, missing or mismatched durable records, disclosure during restore and during blocked lease acquisition, shutdown with queued writes, worker crash/restart and a second tab seeking the same writer lease. An audit nested-worker check must prove cancellation and exact-head rejection. These are acceptance cases, not completed measurements.

## Decisions still required before coding

- The shared `GameSession.validate()` and form API needs an async online contract. Treating it as synchronously authoritative from a main-thread mirror is incompatible with the required boundary.
- Decide whether Stage 07's "online protocol" includes pre-game lobby, chat and WebRTC's device-key signatures. This design places the certified ceremony and game in the worker, while retaining transport and pre-certification UI protocols on main; a literal all-crypto reading requires a larger transport signer migration.
- Verify nested audit-worker bundling and worker Web Locks/IndexedDB in the supported browsers. If nested workers are unavailable, move audit execution to a separate main-created worker without transferring the live voting key or trusting its result as a certified transition.
- Extend `GameWriterLease` with immediate loss signaling before the signer runs in a worker; the current `run()`-only check leaves a gap after unexpected lock loss.
- Measure the longest single proof verification. Queue bounds alone cannot prevent one synchronous verifier from delaying protocol timers; any failing measurement requires a bounded in-worker verifier before the migration can claim full Stage 07 execution compliance.
